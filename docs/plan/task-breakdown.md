# SDD 落地任务拆分

目标：在不改变 LiteDiff 业务行为的前提下，建立轻量、可执行、适合多人协作和 AI 编码的 SDD 工作流。

## 阶段与任务

### Phase 1：基线与边界

| ID | 任务 | 优先级 | 工作量 | 依赖 | 验收标准 |
|---|---|---|---|---|---|
| P1.1 | 确认范围、目标和约束 | P0 | S | 无 | 明确整仓库、轻量 SDD、保留现有改动、不重写业务代码 |
| P1.2 | 盘点架构、入口和模块 | P0 | M | P1.1 | `docs/analysis/project-overview.md`、`module-inventory.md` 完成 |
| P1.3 | 识别安全和性能回归风险 | P0 | M | P1.2 | `risk-assessment.md` 列出优先级和控制措施 |

### Phase 2：SDD 核心制度

| ID | 任务 | 优先级 | 工作量 | 依赖 | 验收标准 |
|---|---|---|---|---|---|
| P2.1 | 编写项目 constitution | P0 | S | P1.3 | 原则可直接用于评审，不是空泛口号 |
| P2.2 | 定义分级变更工作流 | P0 | M | P2.1 | 明确 L0-L3 路径、状态和产物 |
| P2.3 | 编写质量门禁和验证命令 | P0 | M | P1.2 | 命令可执行，覆盖 Rust、前端和构建 |
| P2.4 | 固化安全与性能不变量 | P0 | M | P1.3 | 每项有检查点和验证位置 |
| P2.5 | 记录采用轻量 SDD 的 ADR | P1 | S | P2.1 | 包含背景、决策、替代方案和后果 |

### Phase 3：规范体系

| ID | 任务 | 优先级 | 工作量 | 依赖 | 验收标准 |
|---|---|---|---|---|---|
| P3.1 | 建立 specs 目录、模板和状态规范 | P0 | M | P2.2 | 新变更可直接复制模板开始 |
| P3.2 | 编写当前产品基线规范 | P0 | L | P1.2、P2.4 | 需求可验证，包含非目标、限制和测试映射 |
| P3.3 | 为本次 SDD 落地建立变更记录 | P1 | S | P3.1 | spec/plan/tasks/verification 完整 |

### Phase 4：贡献者和 AI 集成

| ID | 任务 | 优先级 | 工作量 | 依赖 | 验收标准 |
|---|---|---|---|---|---|
| P4.1 | 编写根目录 AGENTS.md | P0 | S | P2.2 | AI 代理能按正确顺序读取规范和门禁 |
| P4.2 | 编写 CONTRIBUTING.md | P1 | M | P3.1 | 新人能完成安装、开发、验证和提交 |
| P4.3 | 增加 PR 模板 | P1 | S | P3.1 | PR 强制关联变更规范、测试和风险 |
| P4.4 | 创建项目级 LiteDiff SDD Skill | P1 | M | P2.2、P3.2 | 通过 skill validator，能路由到正确文档 |
| P4.5 | 从 README 链接开发规范 | P2 | S | P4.1、P4.2 | 中英文 README 都能找到入口 |

### Phase 5：验证与交付

| ID | 任务 | 优先级 | 工作量 | 依赖 | 验收标准 |
|---|---|---|---|---|---|
| P5.1 | 验证前端测试、类型检查和构建 | P0 | M | P2.3 | `npm test`、`npm run check`、`npm run build` 通过 |
| P5.2 | 验证 Rust 格式、Clipy 和测试 | P0 | M | P2.3 | `cargo fmt`、`clippy`、`test --workspace` 通过 |
| P5.3 | 验证验证脚本 | P0 | S | P2.3 | macOS/Linux 脚本可执行，Windows 脚本语法审查 |
| P5.4 | 检查文档链接、模板和 Skill | P1 | S | P3、P4 | 无断链、无占位残留、skill 校验通过 |
| P5.5 | 最终差异审查 | P0 | M | P5.1-P5.4 | 只引入 SDD 文档和工具，不改变运行时行为 |

## 并行执行通道

| 通道 | 可并行任务 | 写文件范围 | 合并风险 |
|---|---|---|---|
| Lane A | P1.1-P1.3 | `docs/analysis/` | 低 |
| Lane B | P2.1、P2.2、P2.4 | `docs/sdd/` | 低，需统一术语 |
| Lane C | P2.3、P5.3 | `scripts/`、质量门禁文档 | 中，命令必须一致 |
| Lane D | P3.1-P3.3 | `specs/` | 中，模板与产品规范需统一状态字段 |
| Lane E | P4.1-P4.5 | 根文档、`.github/`、`.codex/skills/` | 中，引用路径必须一致 |

本次由单个代理顺序执行，以避免多个未提交工作区改动产生冲突。

## 完成定义

- 新开发者能从 README 找到贡献流程。
- AI 代理从 `AGENTS.md` 能找到 constitution、产品规范、变更模板和验证命令。
- 小型修复不需要全套文档，跨模块或高风险改动必须留下可追踪规范。
- `scripts/verify.sh` 能覆盖当前项目的核心质量门禁。
- 本次改动不改变应用运行行为。
