# ADR 0001：采用轻量、仓库原生 SDD

- 状态：Accepted
- 日期：2026-11-06
- 决策范围：整个 LiteDiff 仓库

## 背景

LiteDiff 已具备清晰的差分核心、Tauri 安全边界、前端虚拟滚动和较完整的测试，但缺少统一的产品基线、变更分级、跨会话进度和 AI 编码代理入口。随着安全和性能改动增加，仅靠代码注释和口头约定容易产生规范漂移。

完整 SDD 工具链可以生成大量结构和命令，但 LiteDiff 是一个中小型、单仓库桌面项目。引入外部 CLI、强制全套文档或依赖特定 Agent 会增加维护成本，反而让开发者绕开流程。

## 决策

采用轻量、仓库原生的 SDD：

- 使用 Markdown 作为规范和决策制品。
- 用 L0-L3 分级控制流程强度。
- 维护一份长期产品规范和按变更编号组织的短期规范。
- 把安全和性能不变量直接写入质量门禁。
- 提供 `AGENTS.md`、项目级 Codex Skill、PR 模板和一键验证脚本。
- 不引入 GitHub Spec Kit CLI，不要求特定宿主或云端服务。

## 原因

- 与现有 Rust/Tauri/Svelte 工作流兼容。
- 不改变运行时依赖、构建链路或发布流程。
- AI 代理和人类开发者读取同一组事实来源。
- 小改动保持轻量，高风险改动仍可追踪。
- 以后若团队需要，可在不推翻现有目录的前提下接入 Spec Kit 或其他工具。

## 替代方案

### 直接采用 GitHub Spec Kit

优点：流程成熟、工具和模板丰富。

未采用原因：当前项目不需要额外 CLI 和集成层；完整命令链对小修复偏重。

### 只使用 Issue/PR 描述

优点：成本最低。

未采用原因：无法稳定保存产品基线、风险分析、验收映射和跨会话上下文。

### 每次改动强制完整 SDD

优点：一致性最高。

未采用原因：文档/文案和小修复会产生明显仪式成本，最终容易被绕开。

## 后果

正面：

- 变更可以从问题追溯到实现和验证。
- AI 代理在开始编码前有明确读取顺序。
- 安全和性能边界成为可评审条款。
- 新人可通过单一入口理解架构、测试和贡献流程。

代价：

- 维护者需要同步产品规范和变更状态。
- L2/L3 变更增加文档成本。
- 需要定期检查文档是否与代码和测试漂移。

## 后续验证

- 至少用本规范完成一次真实 L2 功能开发。
- 至少用轻量路径完成一次 L1 bugfix。
- 观察 2-3 个变更后，评审是否需要简化模板或增加自动化。
- 若仓库扩展到多团队或多产品，再评估迁移到专门 SDD 工具。
